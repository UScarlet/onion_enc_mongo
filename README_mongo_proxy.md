# README — MongoDB proxy project

Проект реализует прокси для MongoDB, работающий на уровне MongoDB Wire Protocol, умеет читать полные wire-сообщения MongoDB, определять тип сообщения по `opcode`, распаковывать `OP_COMPRESSED`, разбирать сообщения `OP_MSG`, логировать содержимое запросов и ответов, а также модифицировать `OP_MSG` перед отправкой дальше.

Файл `main.py` является точкой входа в программу. Он создаёт объект `MongoProxy` и запускает его через `asyncio.run(...)`. 

Файл `proxy.py` реализует сетевой слой прокси. 
Он принимает входящие подключения клиентов, открывает соединение к настоящей MongoDB, встаёт между ними. 
Создаёт два асинхронных канала передачи данных — от клиента к серверу и от сервера к клиенту, 
читает полные MongoDB-сообщения, передаёт их в инспектор и трансформер, а затем пересылает дальше. 
По сути, это основной модуль, который связывает все остальные части проекта в единую работающую систему.

Файл `wire.py` отвечает за низкоуровневую работу с MongoDB wire protocol. В нём находятся основные константы протокола, такие как `MSG_HEADER_SIZE`, `OP_MSG`, `OP_COMPRESSED` и `FLAG_CHECKSUM_PRESENT`.

Файл `compression.py` отвечает за работу со сжатыми MongoDB-сообщениями формата `OP_COMPRESSED`. 
Поддерживает алгоритмы `noop`, `snappy`, `zlib` и `zstd`. 
Преобразует `OP_COMPRESSED` в `OP_MSG`, умеет упаковать изменённое сообщение обратно. 
Этот модуль важен для того, чтобы прокси мог корректно анализировать и модифицировать сжатый трафик.

Файл `op_msg.py` предназначен для разбора и сборки сообщений формата `OP_MSG`. 
Он извлекает заголовок, флаги, секции и checksum, а затем позволяет собрать `OP_MSG` обратно после модификации. 

Файл `transformer.py` отвечает за модификацию сообщений. 
Он принимает исходное wire-сообщение, определяет, нужно ли его менять, разбирает `OP_MSG`, изменяет нужные BSON-поля, 
собирает сообщение обратно и при необходимости снова упаковывает его в `OP_COMPRESSED`. 

В текущей версии проекта здесь используется демонстрационная логика подмены значений (name -> name_new), однако именно этот модуль является основой для будущего внедрения шифрования полей.

Файл `big_inspector.py` представляет собой подробный инспектор сообщений. 
Файл `small_inspector.py` реализует краткий инспектор сообщений. Только самое важное: имя команды, базу, коллекцию, фильтр, количество документов, первый документ, число затронутых записей и краткие сведения об ответе.
Файл `inspection.py` выполняет роль переключателя режима логирования. Он считывает значение `INSPECTOR_MODE`, выбирает, какой инспектор следует использовать — подробный или краткий, — и экспортирует функции `inspect_message` и `summarize_parsed_op_msg`. Это единая точка выбора между двумя форматами логирования.


## Как проходит запрос через проект

Типичный путь запроса выглядит следующим образом. Сначала `main.py` запускает прокси. Затем `proxy.py` принимает подключение от клиента. После этого `wire.py` считывает одно полное MongoDB-сообщение из TCP-потока. Далее `inspection.py` выбирает подходящий инспектор, а `big_inspector.py` или `small_inspector.py` формируют текстовое представление сообщения для логов. Если сообщение оказалось сжатым, `compression.py` распаковывает его. Затем `op_msg.py` разбирает структуру `OP_MSG`. После этого `transformer.py` при необходимости изменяет BSON-содержимое. Далее `op_msg.py` собирает `OP_MSG` обратно, а `compression.py`, если это требуется, повторно упаковывает сообщение. В конце `proxy.py` отправляет полученный результат в MongoDB, а ответ проходит аналогичный путь в обратном направлении к клиенту.
